How to read it

  • The map (§1) reads left to right, then down: a brief arrives → event and lineup → landing page and D2C → audiences → campaign in MML with the Insights rail → Creative Lab and the asset bank → launch → reporting and the learning loop, which feeds back into the rail. Operator pages that serve every stage sit underneath. Each card now lists its capabilities as rows with a state; §1A is the same list as a table with code, store and live rows.
  • Each card has a state: Live Partly built Designed, not built Not designed. A ✋ You approve marker means nothing moves until Matas says yes. A ⚙ Runs itself marker means the tool acts on its own and reports what it did on Today.
  • §1B draws the learning chain: eight links, each marked live, partly or missing from live row counts. §1C is the expert layer: per discipline, what the tool knows (with the code) and what it should (tagged deck rule, learning job or watch).
  • §2–§4 redraw the three pages Matas lives in, unchanged from issue 1. §5 lists the gaps, re-ranked. §6 is how this map stays true, with three new rules.
  • To check a PR: find its card and its row. The PR moves the row's state, or it shouldn't touch that area.

1C · The expert layer — what the tool knows, and what it should

Matas wants the tool to hold five disciplines: senior promoter, paid media manager, graphic designer, D2C specialist, behavioural psychologist. Each card names what the tool knows today, with the code that knows it, and what it should know. Every "should know" is tagged: deck rule goes into the Off/Pixel deck as a rule Cursor builds to; learning job is a nightly job writing a store the rail reads; watch is a dated platform fact the tool checks for change. The paid media card owns the platform-change watch.

Count: 25 "should know" items: 13 deck rules, 9 learning jobs, 3 watches. 6 · Keeping it current

  • Same PR, same card. A PR that changes an area's state also changes that card's state in this map, by issuing the next map record with the card moved and a changelog line, in the same PR or its paired docs PR. The reviewer checks the card moved.
  • Card before build. A new area gets its card (state Not designed or Designed) before any build PR for it. No card, no build.
  • Every capability has a row. (Issue 2.) Anything that runs, a cron, a table with a writer, a flag-gated path, is a row on a card with its state. A capability with no row is this record's failure: add the row, then move the card. Removing a row needs a changelog line saying why.
  • A chain link is a gap until it carries rows. (Issue 2.) The learning chain in §1B is checked on every re-issue against live counts. A link marked missing or partly stays in §5 until rows flow and something reads them.
  • Expert items have a home before they're built. (Issue 2.) A deck rule goes into the deck record; a learning job names its store and reader on the Learning loop card; a watch names its platform fact and date. None is built from a chat message.
  • Re-issue, never edit. The map is re-issued as docs/design-record/YYYY-MM-DD-north-star-{n}.html. The new issue copies the last one, extends the changelog at the top, and changes only what moved. Old issues stay as they were.
  • States mean exactly this. Live = on main, used on real data, with rows. Partly built = on main with a named part missing, empty, flag-off or stale. Designed = a record exists. Not designed = no record yet.
  • Markers are rules, not decoration. A ✋ on a card means no code path may act there without Matas's yes. Adding or removing one is a design ruling, so it needs a record.
  • Review checklist addition. Every design review states the card(s) and row(s) it touched and their state after the PR.
