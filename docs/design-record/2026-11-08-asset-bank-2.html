A · Rulings (A1'–A5' replace issue 1's A1–A5; A6', A11 new; A7–A10 stand)

#Ruling
A1' A release is a name, two times and a stateA release has: name, community time, list time, and a state: not yet · on sale · selling fast · final X · sold out. Price and capacity are optional and shown only when known; a count is optional and shown only when entered or synced. A release with no community time is public. events.presale_at = the first release's community time and general_sale_at = the general-sale release's list time, both derived, as before.
A2' The timeline carries the ladderReleases draw on one horizontal line with today and the next payday marked. Under each release sits its ladder: the warning claims it has made, is about to make, and may make, as rungs (done · next · later). A release's state and its ladder are the same thing read two ways: the state is the rung it's on. No fixed set of six assets per event; the ladder is per release and per client.
A3' Sold entry is a state, one gestureMatas sets a release's state by tapping its segment: not yet · on sale · selling fast · final X · sold out. That's the whole entry; it saves with the date, his name and the source (vendor page, client message). A count is an optional chip beside it (add a count) that becomes a number when tapped; it never blocks the state. Never a form. The panel's big number is the number of releases on sale or selling fast, not a sold total, unless every release has a count. A state can move backwards (a release reopened) and asks once when it does.
A4' The vendor read proposes; Matas correctsMon / Wed / Fri at 09:00 the tool reads the event's ticket page and writes what it saw per release (state, and a count or remaining if the page shows one). From that read and the claim ladder it proposes the next rung for each release that has moved, as a proposal card: what was read, what it proposes to push, Approve / Correct. Correct opens the state control inline; a corrected read becomes Matas's entry with his name on it. A client message does the same job by hand: Matas sets the state and the proposal follows. The reader is to be proved (data note); the card is the same either way.
A5' The claim ladder: trigger → claimWarnings are claims, and the ladder says which claim a trigger allows. Two columns. Trigger: what's actually true, from a count (actual sold ÷ capacity when both are known), a remaining figure from the page, or the release state and days on sale when there is no count. Claim: what the asset says. Matas's default ladder: actual 50% → "75% sold"; 60% → "80%"; 70% → "90%"; 80% → "95%"; 90% → "99%" or "final X". With states only: on sale (day 0) → "{release} live / selling fast"; selling fast for 7+ days → "{release} 90% sold out" or "final X {release} tickets" (client's choice); final X → "final X"; sold out → "sold out". Each client has their own ladder, edited as the component in AB5; the default is seeded. A claim never runs above its trigger, and the trigger is recorded on the approval (A6').
A6' Approve, with the trigger on the cardEvery proposed claim is an approval card: artwork preview, the claim it makes, the trigger that allows it (the read or the entry, with source and time), and when it runs. Approve → Scheduled → Live. A claim whose trigger is not yet met is locked and says what would unlock it. A claim whose trigger moves after approval (a corrected read, a reopened release) goes back to Held with one sentence saying why, and Today gets a row. Nothing runs without Approve.
A7–A10Stand as issued in issue 1: payday window and content-led mid-month (A7), payday exceptions (A8), the board tells the truth about what's missing (A9), 393 (A10). In A7, "Presale live" and "General sale live" become "{release} live" for any release; it still runs at the release time whatever the calendar says.
A11 The ladder and the caption validator — ruling for MatasProposal: an approved warning is a promoter claim with its trigger recorded. The caption validator (caption-facts.ts) accepts a caption that repeats an approved, live claim's words for that release ("90% sold out", "final 50") while the claim is live. Everything else keeps the strict rule: a caption that says "sold out", "final" or "under N" on its own must be literally true. So the Lab can echo what the warning already says, and can't invent more. The alternative is to loosen the validator to the ladder everywhere, which makes every caption a claim; not proposed. Needs Matas's yes before H4 is built.

AB1 · Releases with states and ladders, and the state entry (1280 and 393) — redrawn

The state control is the entry: one tap, saved with date, name and source. The ladder under each release on the timeline is what has been claimed, what's next and what may come; the Claims panel lists the same rungs with their run state. A count is a chip until Matas or a sync fills it; when a count exists the trigger uses it, and the ladder's percentage rungs read against it.

AB2 · The proposal card and the approval card with its trigger (1280 and 393) — redrawn

The proposal card is Matas's example drawn: the read in mono, the trigger and the claim side by side, Approve or Correct. Correct opens the state control inline on the card; the corrected state is saved as his entry and the proposal recomputes. When the reader isn't proved yet, the card's first line reads Client message, Wed 4 Nov: and the rest is identical (H9). The X in "final X" is always a figure the page or a count supplied; the card never asks him to type one.

AB3 · Payday calendar — kept from issue 1, pushes renamed to ladder claims

AB3-1280 and AB3-393 stand as issued in #1107, with these label changes only: "Price rise 1 Dec" → "3rd release 90% sold out" (in the payday window), "3rd release live 12:00" stays, "Final 100 · if true" → "Final X · 3rd release · if triggered", "Last day at £26" is removed (no price push). A7 and A8 unchanged. Not redrawn here, so the frame ids and baselines stay.

AB4 · The board — one row per release ladder (1280 and 393) — redrawn

AB5 · The claim ladder — trigger → claim, per client (1280 and 393) — new

The ladder is one component, drawn once, edited per client on the Ticketing tab. Matas's numbers are the seed; a client's ladder can differ (Puzzle: 5 days to the 90% line, and the % wording over "final X"). The trigger column is what the read or the entry must show; the claim column is what the asset says. The approval card quotes the rung it used, so every claim is traceable to the trigger that allowed it (A6').
