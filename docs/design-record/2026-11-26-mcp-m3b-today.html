M3b’s changes on Today’s log

M3b (#1389) shipped switched off, because the consent page promises “every change is listed on Today”. FC1 already made Today a log. This record gives Today the rows, Undo and scheduled changes M3b adds, so the builder can switch M3b on. FC1 stands as written, and the merged records aren’t edited.

  • Each M3b change is an FC1 row: title, change line, “Approved in Claude · {date, time}” with What Claude asked, the outcome, and Undo where one exists.
  • A budget change set for later sits at the top of the section until it runs, with Cancel.
  • Reads, and refusals that are only a mistake in what Claude sent, aren’t logged.

Rulings

#Ruling
MB1 · M3b’s rows
  • Each change is one row, in FC1’s form, newest first. The title and change line per tool:
    • pause and resume: “Pause campaign”, “Pause ad set”, “Pause ad”, and the same with Resume; “{name}: live → paused”, and the reverse;
    • set_budget: “Change budget”; “{name}: £{x} → £{y} a day”, or “lifetime” for a lifetime budget. When the old amount wasn’t recorded: “{name}: to £{y} a day”;
    • move_budget: “Move budget”; “£{x} a day: {from} → {to}”;
    • rename: “Rename”; the change line is “{before}” → “{after}”, both names in quotes, because names carry “·”;
    • add_creatives_to_stage and add_audience_to_stage: Step 0’s rows as they are;
    • create_split_test: “Start an A/B test”; “{a} vs {b} · 50/50 · {start} – {end}”.
  • Outcomes use TD’s counts-only results. A test counts as “1 test created · {id}”. A change Meta refused outright reads “Failed · Meta didn’t take it, so nothing changed”. A move that only lowered one side reads TD’s “Failed · 1 of 2 ad sets changed · {id}”.
  • Undo, in FC1’s form, where M3b can put it back:
    • pause and resume, budget change and move: FC1’s lines. A lifetime budget reads “Undo puts it back to £{x} lifetime.”;
    • rename: “Undo puts the old name back.”;
    • creatives added paused: FC1’s delete line. Added live: FC1’s “It’s live, so Undo can’t delete it. Pause it in the campaign tree.”
  • No Undo on added audiences (nothing to say), a part-done move, or a test. A test’s row reads “A test can’t be undone here. End it in Ads Manager.”
MB2 · Scheduled budget changes
  • Before it runs: a set_budget with a time is a row from the moment Matas says yes. It sits at the top of the section, soonest first, on every day until it runs. Beside the title, the header adds “{n} scheduled”.
  • The row shows the change line and “Approved in Claude · {date, time} · What Claude asked”, then, with an ochre edge, “Scheduled for {date, time}”. Under that are Cancel and “It runs only if nothing has changed by then.”
  • Cancel is Matas’s own action and doesn’t confirm, because nothing has run. The row then reads “Cancelled by {name} · {date, time}”, muted. Claude’s cancel_scheduled reads “Cancelled in Claude · {date, time}”.
  • When it’s due the row moves into the day’s log at its run time and adds “Ran as scheduled · {date, time}” under the approval line. Then it shows:
    • Done, with the budget Undo;
    • or, muted, “Skipped · {reason}”. The reasons are the six told to Claude by list_scheduled, in lower case: the budget changed, it was paused, it ended or was deleted, the ceiling, the switch, or Meta couldn’t be read;
    • or “Failed · Meta didn’t take it, so nothing changed”. A budget that changed during the write reads as skipped for that reason.
MB3 · What the log leaves out
  • get_live and list_scheduled read only, so they have no row.
  • Refusals: FC1’s rule stands. Muted rows for the reasons Matas acts on: no approval, ceiling, no ceiling, switch.
  • Refusals that only correct what Claude sent stay out of the log. Claude is told each one, and the action log keeps them. Examples: wrong id or event, a budget type mismatch, bad dates, an unknown template.
MB4 · Switching M3b on
  • The PR that builds MB1–MB3 sets LIVE_CHANGES_SHIPPED and TODAY_UNDO_SHIPPED to true together. From then on, “Matas can undo this on Today.” goes out wherever an Undo exists (FC2).
  • Neither flips on its own. Until both rows and Undo are on Today, the consent line’s “every change is listed on Today” isn’t true.

Acceptance

  • Every M3b write is a row, with the question and answer exactly as stored, including a scheduled change from the moment it’s approved.
  • Undo: FC1’s acceptance holds for each M3b Undo, and a test checks each pair, rename included. No Undo appears on added audiences, a part-done move or a test.
  • Scheduled:
    • a row waits at the top until it runs, then moves to its run time;
    • Cancel on Today stops it, with the same rule as cancel_scheduled: only while it’s still scheduled;
    • a skipped or failed run shows its reason, and nothing raw from Meta.
  • Switch: LIVE_CHANGES_SHIPPED and TODAY_UNDO_SHIPPED flip in the same PR as these rows, and a test pins them together.
  • Words: every string is a row, exactly.
