Audio snippet statics and the test plan

From Matas, 16 Nov. Puzzle gives Off/Pixel free rein on its ads and creatives, so Puzzle is where two new things start:

  • the audio snippet static: a static with 15–20 seconds of one of the act's top tracks, around its main drop;
  • the test plan: tests in a fixed order that find the best track, then the best static, then run the two together. It's built for every client, not just Puzzle.

This record also notes three things carried over: the copy A/B test now running as GK9's house-pattern test, the GK9 ruling on series events, and #1270 closing WB9's retry gap.

It builds on the on-sale refresh (R2 pause lines, R4 Accept and shadow, R5 the plan guard, R6 scoring), the overlay records' 9:16 rules (O93, O95, O96), the Drive tree (S18, D1–D5) and S14's file names. Those all stand. Every value not taken from an earlier record is listed under "Invented here". The example tracks, spend and results are invented.

Rulings

#Ruling
CT1 · The format
  • An audio snippet static is a video: one still image held for the whole snippet, with the snippet as its only sound. Meta runs sound only on video, so it follows the video rules: one 9:16 render at 1080 × 1920 (O93, O95), its type inside O96's band.
  • The image is an existing static's 9:16 render, unchanged: a T2 card, an artist card or a poster. Its 4:5 and 1:1 stills stay stills and aren't touched.
  • No words are added for the track: no title and no "now playing". In Test 1 the image must be identical across the variants, so only the sound differs.
  • Length is 15 to 20 seconds, 16 by default: from 4 seconds before the drop to 12 seconds after it.
  • Sound: a 0.25 s fade in, a 1.5 s fade out, loudness normalised to −14 LUFS with peaks no higher than −1 dBTP, AAC at 256 kbps.
  • File name (S14 pattern): {event code}_{artist}-{track n}_snippet-{static}-{stage}_r{n}_9x16.mp4. {track n} is the track's place in the picker, and {static} is the static's own S14 name. It files under Videos for the track's artist (D1, D2).
CT2 · Where the audio comes from, and the rights note
  • One source: audio files in the event's Drive folder, 02 Source / Audio / {artist}, named exactly as the Lab lineup. The folder is made on first need (D5).
  • No way in from a link. The Lab has no field for a YouTube, SoundCloud or Spotify link, and never downloads audio from anywhere. Spotify is read only for the list of tracks (CT3). This makes "never ripped" true by construction, not by trust.
  • Accepted files: WAV, AIFF, FLAC, or MP3 at 256 kbps or more, and at least 30 seconds long. Anything else is shown as "Can't use this file: {reason}".
  • Who supplied it is recorded. The first time a file is used, the Lab asks "Who supplied this file?" with the choices "{client}" and "{artist}'s team". It stores the answer with who picked it and when. A file without an answer is held: "Name who supplied this file before it can run."
  • The rights note sits under every track that has a file, and on the snippet's render row: "Audio supplied by {supplier} · {file name} · {who}, {date}".
  • The client's free rein on ads covers how Off/Pixel uses files the client or the artist's team supplied. It doesn't stand in for the supplier step, which records it per file.
CT3 · The track picker
  • Act chips in billing order, the same lineup the Lab uses. One act's tracks show at a time.
  • Spotify's top tracks for that act, up to 10, in Spotify's order, as "{n} · {title}". The order is Spotify's popularity ranking and is never re-sorted.
  • Each row's file state:
    • a matched file: the rights note (CT2);
    • a suggested match: "Looks like {file name}" with the action "Match". Matching is by title, and an operator confirms it;
    • no file: "No file in Drive yet", and the row's tick is off.
  • Only rows with a matched, supplied file can be picked. The count reads "{n} of 5 picked". Test 1 takes 2 to 5 tracks.
  • From Drive only: an audio file in the folder that matches no Spotify top track is listed under them as "{file name} · not in Spotify's top tracks". It can still be picked.
  • The Spotify read is cached per act for a day. When Spotify doesn't answer: "Spotify didn't answer, so the top tracks can't be listed. Pick from the Drive files below."
CT4 · The drop marker
  • The Lab finds the drop when the file is first matched: the biggest rise in low-end energy after a build, past the first 20 seconds.
  • The waveform shows the whole track. On it:
    • the drop marker, a brick line with "DROP · {m:ss}";
    • the snippet window, a box over the waveform, by default from 4 s before the drop to 12 s after.
  • Both can be moved. Drag the marker to set the drop, which moves the window with it. Drag the window to move the start alone.
  • Length chips: 15 to 20 seconds, one chip each.
  • The source line reads "Drop found by the Lab" or "Drop set by {first name}".
  • No clear drop: "No clear drop found. Drag the marker to where it lands." No snippet renders until a marker is placed.
CT5 · The preview
  • Beside the waveform: the rendered 9:16 at phone size, with one play / pause button. It plays the snippet exactly as it will run, fades and loudness included.
  • Under it, the snippet's span: "{start}–{end} · {length} s".
  • Each change to the marker, window or length re-renders the preview after a 1-second pause. A failed render reads "Preview didn't render. Try again."
CT6 · The test plan
  • A test plan belongs to one event. It holds tests in order, and each test changes one thing and holds the rest. They're called tests, not rounds: the Lab and S14's _r{n} already use "round" for writing rounds, and two meanings of one word on one screen would mislead.
  • Puzzle's plan, and the default for any client:
    • Test 1 · Tracks: 2 to 5 snippets, the same static, one track each.
    • Test 2 · Statics: 2 to 5 statics, all carrying Test 1's winning track.
    • Test 3 · Together: Test 2's winner (which carries both winners) runs in the main on-sale campaign beside that campaign's current best ad, to confirm it before it scales.
  • Other kinds of test: a test can change the copy instead (CT12), or the clip. A plan can be one test long.
  • A clean test: each variant gets its own ad set in one test campaign, {event code} · Test {n} · {kind}, with the same audience, placements, optimisation and daily budget. That way Meta's delivery can't pick a favourite before the result is in. Test 3 runs in the main campaign as R2 add lines.
  • Each test's settings: the result it's judged on, a daily budget per variant, a minimum number of days and a minimum spend per variant.
    • The result is the campaign's own (R3): checkouts, else landing-page views, or signups on a signup campaign.
    • Defaults: £10 a day per variant, at least 4 days, at least £40 per variant.
  • Money: a test's budget is shown as "£{daily} a day × {n} variants × {days} days = £{total}" and comes from plan headroom or a named move (R5). A test that doesn't fit the plan can't start: "This test needs £{total} and the plan has £{headroom} left."
CT7 · The winner rule, and what a test says
  • No winner is called before every variant has had both its minimum days and its minimum spend.
  • When they have:
    • The winner is the variant with the lowest cost per result.
    • Clear means it's at least 15 % cheaper than the next one, and both have 20 results or more.
    • Too close: the test runs on for the minimum days once more. After that, the cheapest wins and is marked narrow.
  • Not enough results: when any variant has fewer than 5 results at its minimum spend, no winner is called. The test reads "Not enough {results} to call this. Raise the budget or judge on {next result}."
  • States, as the event page shows them:
    • "Running · day {d} of {min days} · £{spent} of £{min spend} each";
    • "Ready to call";
    • "Too close · running {n} more days";
    • "Winner: {variant} · {pct} % cheaper per {result} than {runner-up}", with " · narrow" added when it is;
    • "Waiting for Test {n−1}".
  • Calling is Matas's click, "Call the winner", as R4's Accept. A call is stored with its evidence snapshot.
CT8 · After a call
  • Losers become R2 pause lines in the event's refresh panel, as the rule "Lost Test {n}". The test is their evidence, so R2's own significance bar doesn't apply to them. They still need Accept, and shadow mode applies (R4).
  • The winner moves on. Test {n+1} holds it as the fixed part and starts once the Lab has made its variants: "Make Test 2's statics with {track}".
  • Test 3's winner stays in the main campaign and joins the refresh's normal creative care. If the current best ad wins, the plan ends: "The current best ad held. Nothing changes."
  • R6 scores calls too. A call is right if the winner's cost per result, over its next 7 days in the main campaign, is no worse than 1.15 × what it showed in the test.
CT9 · The event page
  • A "Test plan" panel under the Refresh panel, with one card per test in order.
    • A card shows the test's name, what changes and what's held, its budget line, its state (CT7), and its variant table: variant, spend, results, cost per result, and "vs best".
    • The running test is open. Finished and waiting tests are folded to one line.
  • On a phone the table becomes rows of "{variant} · {cost per result} · {results}", with the state above them.
  • The canvas chip reads "Test {n} running" or "Test {n} ready to call".
CT10 · The Lab
  • A "Snippet" tab beside the writer holds CT3–CT5: act chips, the track picker, then the waveform and preview for the track that's open.
  • "Make Test 1" renders one snippet per picked track on the chosen static. A static is chosen from the event's approved 9:16 statics: "Static: {name}".
  • Render rows carry the test tag "Test {n} · {variant}" and the rights note. They file to Drive by S14, as CT1.
  • A snippet is approved like any render. It can launch only as part of a test or as an R2 add line.
CT11 · The client share
  • "What we're testing" on the client's share link, under the creative section. It shows each test's name and what it changes, the state as CT7 words it, and its variant table, which is figures only (PH3): results and cost per result.
  • It never shows budgets, pause lines, Accept or calling, the supplier step, or any internal note.
  • Variant names are the track titles or the statics' names. A copy variant shows its first line.
CT12 · Carried over
  • The copy A/B test is GK9's house-pattern test. Matas's call was to test, not watch. It's running on NX Newcastle, Kream and Puzzle: artist voice, name first, date in the body, against venue voice. It's registered as a one-test plan per event, of kind Copy, with CT7's winner rule. Its results feed the genre pool's shadow rows (GK3) like any other learning, and its calls are scored by R6.
  • GK9 · series events (Matas, 16 Nov):
    • Each Bridger or Junction 2 event takes its own genre, as GK1 says. A series never gets a genre of its own.
    • A series or umbrella parent isn't a show (PT3), so it gets no genre and never counts in a pool. "No single genre" is only for a show that mixes genres.
    • GK2's suggestion reads only that event's own genre tags and lineup.
    • Each event counts as a show, but a series is one client.
    • Junction 2 is active and its history is loaded, so its shows count. GK8's unarchive item is closed.
  • WB9's open item is closed by #1270 (merged 1490bdb), as ops reported it. Every retry re-checks the stored funding against live headroom, the £1.00 a day floor and the 20 % cap, and refuses with the same reasons as a first apply. CBO lines are unaffected.

Frames

In CT-A, track 5 is picked but held: its file has no supplier yet, so "Make Test 1" waits until it's named or unticked.

CT-D has no budgets, refresh lines, supplier step or call button: the share link only reads the results.

Acceptance

  • The Lab has no field or path that takes audio from a link. A test asserts that the snippet renderer reads only from 02 Source / Audio.
  • A snippet can't render without a confirmed match, a named supplier and a placed drop marker.
  • Renders are 9:16 only, at the loudness and fades in CT1, named by CT1's pattern.
  • No winner is called before both minimums are met. Clear, too close, narrow and not-enough-results each have a test.
  • Losers reach the refresh only as "Lost Test {n}" lines, with Accept and shadow intact.
  • The share link renders CT11's fields and none of the internal ones.
  • Frames CT-A to CT-D at 1280 and 393, from fixtures.
