Rulings

#Ruling
E1 · What counts as a show's purchases (a)

The count that triggers is a count of exactly what the Purchase campaign would optimise on. A figure Meta can't optimise on can't start a campaign that asks Meta to optimise. So the sources rank like this:

  • 1 · Purchases on the show's own domain (the only trigger). The pixel's purchases whose domain is this show's own, read from Meta's domain breakdown on the pixel the ads actually use (E4). This is read-only, and history is there from the first read.
  • The Purchase campaign optimises on the same thing. On Accept, P4 creates a per-show custom conversion on that pixel and points the campaign at it:
    • the rule is Purchase, domain equals the show's own domain, which is the population the count measured;
    • it's named {EVENT_CODE} · Purchase on {domain};
    • it's created as part of Accept's write, never in shadow.
    The campaign never optimises on the pixel's plain Purchase. That would teach Meta to find buyers for any show on the pixel.
  • 2 · Ticketing data, where linked: a check. It shows the pixel's share of real sales. It never triggers, and it never blocks (C6).
  • 3 · Attributed, any show: context. The attributedPurchases figure keeps C2's label and is never the show's purchases.

A show's own domain is a domain that carries this show's page and no other running or upcoming show's. Two places supply it:

  • the event's signup URL host, when no other event in Off/Pixel uses it;
  • when the signup URL is a crqln.com/l/{slug} link, the CIRQLIN custom domain bound to that page.

Never a show's own: crqln.com itself (every CIRQLIN page shares it), ticket sites (Skiddle, Universe, Ingresse), and a tour site shared by several shows. Hosts compare exactly as written, except that a leading www. is the same domain.

Not used:

  • CIRQLIN's own data. CIRQLIN sees signups and ticket-link clicks, never the checkout. A click is not a purchase.
  • A purchase event sent from CIRQLIN. Rejected for the same reason: it would be a purchase invented from a click.
  • A custom conversion on a ticket site's URL or parameter. Not ruled. No URL is readable, and Skiddle's confirmation page doesn't name the show. If a ticket site is later proven to carry the show in a parameter, a later record can add it under source 1.
E2 · The bar and the trigger (b)
  • 15 or more purchases on the show's own domain in 14 days, to the window end, on the resolved pixel. That proposes the Purchase campaign (with E1's custom conversion) and lets budget moves cross campaigns on cost per purchase.
  • Under 15: moves stay inside each campaign, on C9's thresholds.
  • Why 15 stays. The narrower count makes 15 harder to reach, not easier, so the bar gets stricter in effect. It's the floor for putting a proposal in front of Matas, not a promise that Meta's learning is done. Meta's own guidance asks for more per ad set.
  • An own domain that never sees a purchase isn't "under the bar". If it has 0 purchases in 90 days while the pixel has purchases, the show's purchases are landing somewhere else (most often the ticket site's checkout). It takes E3's "nothing reaches" state, not "0, under 15", which would read as if the show might get there.
E3 · What the panel says (c)

F2 below has every state at 1280 and 393. The state is picked in this order, and the first that applies wins:

  1. no pixel;
  2. no page or ticket URL;
  3. ticket site only;
  4. no domain of its own;
  5. shared domain;
  6. nothing reaches the domain;
  7. under the bar or proposed.

Every state keeps the attributed line under it (C2). The ticketing check shows only when ticketing is linked and there's a domain count to compare.

E4 · The pixel (d)
  • Where the true pixel comes from. It's the pixel in promoted_object.pixel_id on the event's ad sets that delivered in the window. When ad sets disagree, it's the one carrying the most spend. If another pixel carries 10 % of the spend or more, the panel adds "{k} ad sets optimise on pixel …{last 4}".
  • The refresh reads it from there, never from the stored field. Every pixel-level read (the domain breakdown, E1's custom conversion, the 90-day check) uses the resolved pixel. IC stays the ads' own reported result, which Meta already ties to each ad set's pixel.
  • A mismatch shows, and nothing is overwritten. When the resolved pixel differs from clients.meta_pixel_id, Objective shows a setup line: "Ads optimise on pixel …2763 (NX LOVES); the client's stored pixel is …4565. Counts use …2763." It isn't a blocker and has no action. Slack carries the same line once per event until the two match.
  • The stored field stays as it is. The refresh never writes clients.meta_pixel_id. It holds one pixel per client, but Electric Brixton's venues each run their own (NX LOVES for Newcastle), so no single value is right for that client. It remains the launcher's default for new launches only. Fixing that default per venue is a later record (open below).
  • No resolvable pixel (no delivering ad set has one): no count and no proposal. The panel says so (F2).
  • Evidence: pixel: { id, source: "ad_sets", spendShare, stored, matches }.
